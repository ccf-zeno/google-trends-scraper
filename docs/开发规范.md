# 开发规范（Development Guidelines）

## 一、通用篇

### 1. 目录结构

核心原则一句话概括：**「按归属划分，而不是按功能类型划分」**。
一个文件应该放在哪里，取决于它「属于谁」，而不是「它是什么类型的文件」。

#### 1.1 归属原则

判断一个文件放哪，按下面顺序走一遍即可：

1. **一眼就能看出是通用代码**（如 `button`、`toast`、`modal`、`loading`、通用格式化函数等）→ 直接放 `src` 全局。
2. **已经有两个及以上页面/模块在用** → 提到 `src` 全局。
3. **只有单个页面在用、且暂时看不出通用性** → 先放该页面目录，等真的出现第二处使用时再提升到全局。

> 原则：**「明显通用直接上提，拿不准的先私有，出现第二处再提公」**。宁可后面把重复代码提升为公共模块，也不要一开始就过度设计出没人复用的「通用组件」。

#### 1.2 目录结构示例

`components`、`hooks`、`utils`、`apis`、`stores`、`types`、`constants` 这些功能类型**共用同一套归属逻辑**。关于「建文件夹还是单文件」：

- `src` 全局的功能类型：**一律建文件夹**存放，即使里面东西很少。
- 页面下的功能类型：**默认用单文件**（`types.ts`、`apis.ts`、`utils.ts`、`hooks.ts` 等），数量多、需要分类时才建文件夹。
- `components` 除外：**必须用文件夹**。

统一示意如下：

```
src/
├── components/          # 通用组件（多页面复用）
│   ├── Button.tsx
│   └── Modal.tsx
├── hooks/               # 通用 Hook
│   └── useTheme.ts
├── utils/               # 通用工具
│   └── formatDate.ts
├── apis/                # 通用接口
│   └── user.ts
├── stores/              # 全局状态
│   └── auth.ts
├── types/               # 全局类型
│   └── common.ts
├── constants/           # 全局常量
│   └── status.ts
└── pages/
    └── home/            # 以 home 页面为例
        ├── index.tsx            # 页面入口
        ├── components/          # 该页面私有组件（必须用文件夹）
        │   ├── Header.tsx
        │   └── ChatInput.tsx
        ├── hooks.ts             # 该页面私有 Hook（数量多时可改 hooks/ 目录）
        ├── utils.ts             # 该页面私有工具
        ├── apis.ts              # 该页面私有接口
        ├── stores.ts            # 该页面私有状态
        ├── types.ts             # 该页面私有类型
        └── constants.ts         # 该页面私有常量
```

#### 1.3 补充约定

- 页面私有代码之间用**相对路径**互相引用；跨页面/跨模块引用用**路径别名**（如 `@/`）。
- 通用代码才允许被页面跨模块 import，页面私有代码**禁止**被其他页面 import。

#### 1.4 类型与常量组织

- 类型定义文件**统一命名为 `types.ts`**，不要叫 `interfaces.ts`。
- 常量放 `constants.ts`：状态用 `enum` 定义，配一个 options 数组（`{ label, value, ... }`）用于渲染下拉、表格等场景。

### 2. 国际化

涉及国际化的项目，开发阶段的写法原则：

- **按「没有国际化」的方式直接写**：UI 文案直接用项目的默认语言写死在代码里，不引入 i18n 逻辑。
- **不要**在写代码的过程中把文案提取成 i18n key，也**不要**顺手翻译成其他语言。
- 国际化是**最后一步、必须由用户手动触发**的独立任务：AI 开发完成后**不得自行**提取或翻译文案；必须等用户确认页面没问题后，明确下达「提取文案到国际化 key」的指令，才统一处理。

### 3. 项目说明书与文档

- 项目根目录的 `AGENTS.md` 是**专门提供给 AI 的项目说明书**，AI 每次任务开始前**必须**先阅读，了解项目背景、技术栈、目录约定与注意事项。
- `docs/` 文件夹**专门存放给 AI 阅读的各类指南**（如接口约定、构建部署、调试方法等），按需取用即可，不需要一次性全读。
- `docs/` 里有哪些文档、各自在什么场景下阅读，统一由 `AGENTS.md` 说明。

### 4. 代码规范

**禁止**把「值」和「类型」复合在一条 import 里引入，必须拆成两条：

```ts
// ❌ 错误
import { clsx, type ClassValue } from 'clsx';

// ✅ 正确
import { clsx } from 'clsx';
import type { ClassValue } from 'clsx';
```

- 工具函数、常量等一律用**声明式导出**（`export function xxx()`、`export const`），并通过目录下的 `index.ts` 统一**桶导出**（barrel export）。

#### 4.1 主流程优先，局部辅助函数后置

当一个函数内部包含多个仅供当前函数使用的辅助函数时，应将**主流程集中写在前面**，将辅助函数的定义统一放在主流程之后。

阅读代码时，首先需要知道的是「先做什么、再做什么」，而不是每一步具体如何实现。辅助函数穿插在主流程中间，会打断阅读节奏，使真正的执行顺序难以快速识别。将它们后置后，可以先一眼看清完整流程；需要了解某一步的实现细节时，再跳转到对应的辅助函数查看。

局部辅助函数优先使用函数声明。函数声明可以在定义前调用，适合将实现细节放在主流程之后。

```ts
// ❌ 不推荐：辅助函数穿插在主流程中，执行顺序不够直观
async function initPage() {
  const loadUser = async () => {
    // 加载用户信息
  };

  const loadPermissions = async () => {
    // 加载权限信息
  };

  await loadUser();

  const loadPageData = async () => {
    // 加载页面数据
  };

  await loadPermissions();
  await loadPageData();
}

// ✅ 推荐：先展示完整主流程，再集中定义实现细节
async function initPage() {
  await loadUser();
  await loadPermissions();
  await loadPageData();

  async function loadUser() {
    // 加载用户信息
  }

  async function loadPermissions() {
    // 加载权限信息
  }

  async function loadPageData() {
    // 加载页面数据
  }
}
```

这里的“后置”仅针对**局部辅助函数的定义**。主流程依赖的变量声明、条件判断和执行语句仍应按照实际执行顺序书写，不应为了追求形式而移动到不自然的位置。

### 5. 注释与文档

代码注释、以及 `docs/` 下的文档编写，**一律使用中文**，**不允许使用英文**撰写注释或文档。

代码注释不要解释太多，太啰嗦。
普通函数、变量无需注释。
重点函数、变量用注释说明是干嘛的即可。
特殊函数、变量用注释说明为什么这么做，实现思路。

文档编写也不要解释太多，太啰嗦，严谨记录改动历史。

## 二、React 篇

### 1. 组件 Props 写法

组件一律用箭头函数。下面这种写法违反了两条规范：

```tsx
// ❌ 错误
const AiMessage = ({ message }: { message: string }) => {
  // ...
};
```

1. **Props 类型需独立定义**，不应在函数参数位置内联书写，否则会降低可读性。
2. **解构需放在函数体内部**，不应在函数参数位置直接解构。

两者均为了提升可读性与一致性。正确写法：

```tsx
// ✅ 正确
type AiMessageProps = {
  message: string;
};

const AiMessage = (props: AiMessageProps) => {
  const { message } = props;
  // ...
};
```

## 三、Vue 篇

### 1. 组件写法

一律使用 `<script setup lang="ts">`（复杂渲染场景可 `lang="tsx"`），**不使用 Options API**。

```vue
<script setup lang="ts">
interface Props {
  modelValue: string;
  disabled?: boolean;
}

const props = withDefaults(defineProps<Props>(), {
  disabled: false,
});

interface Emits {
  (e: 'update:modelValue', value: string): void;
}

const emit = defineEmits<Emits>();

const visible = defineModel<boolean>({ required: true });
</script>
```

### 2. composables

一律 `use` 前缀命名，与组件/模块同目录放 `hooks.ts`。

### 3. 状态管理（Pinia）

一律使用 **setup store**，**不使用对象形式的 store 定义方式**：

```ts
// ✅ 正确：setup store
export const useAppStore = defineStore('app', () => {
  const loading = ref(false);
  const setLoading = (v: boolean) => {
    loading.value = v;
  };
  return { loading, setLoading };
});

// ❌ 错误：对象形式的 store
export const useAppStore = defineStore('app', {
  state: () => ({ loading: false }),
  actions: {
    setLoading(v: boolean) {
      this.loading = v;
    },
  },
});
```
